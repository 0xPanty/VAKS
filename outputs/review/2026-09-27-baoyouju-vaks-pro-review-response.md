# 保有據 × VAKS 独立可行性评审

**总体判断：Conditional Go——值得推进一个范围严格受限的小团队验证，但不支持把现有 VAKS 视为已具备生产能力，也不支持现在扩大成跨公司保险平台。**

| 判断对象 | 结论 | 适用范围 |
|---|---|---|
| 本人先验证一个高频业务流程 | **Go** | 先用合成案例、获准使用的资料和现成工具建立基线，不必先开发完整产品 |
| 3–5 人内部团队 MVP | **Conditional Go** | 资料使用权、人工责任人、真实权限隔离、版本发布和撤回机制落实后，开展限量试点 |
| 现有 VAKS 直接接模型后作为可靠保险助手上线 | **No-go** | 本包没有证明发布、权限、检索、生成、核对和纠错已经贯通 |
| 自动给客户推荐产品、自动发送、跨公司推广、应用商店产品 | **当前 No-go** | 业务效果、授权边界、运营能力和经济性均不足以支持扩大投入 |

**最重要的结论是：你们现在不缺更多架构概念，缺的是一个能够证明“资料适用、输出可核对、权限不会串、更新有人负责，而且确实比原流程省事”的小业务闭环。**

VAKS 有值得保留的基础，但价值不在于“已经拥有一套完整知识服务”，而在于它已经认真区分了来源、证据、审阅、适用性和行动权限。下一步应把这些原则压缩成保险工作流需要的最小实现，而不是让保险业务承担整个通用 VAKS 架构的复杂度。

# 一、VAKS 到底做到哪一步了？

## 1.1 不应给出一个“整体完成度百分比”

当前材料支持四种不同证据层次：

**代码存在 → 当前能够运行 → 对真实业务有效 → 能够可靠对外提供服务。**

这四层不能互相替代。你们已经有部分第一层证据和历史受限实验材料，但没有足够证据把整个保险助手放到第三、第四层。

## 1.2 三个必须特别纠正的理解

### A. 当前检索不是已经完成的混合 RAG

代码明确只有 `local_lexical`，向量、图、融合和第二阶段重排都处于禁用状态。

更具体地说，正文词项评分使用：

```text
body_tokens = Counter(tokenize(doc.body[:20000]))
```

这意味着**正文前 20,000 个字符以后的词项，不直接参与这部分得分**。标题和小节名仍可能命中，所以不能断言后部内容绝对检索不到；但若把该原型直接用于未充分分块的长保险条款，后部除外责任、定义、附表和批注存在漏检风险。

这不是已经观察到的真实保险事故，而是静态代码暴露出的适配风险。**Jev 重排不能补回没有进入候选集的证据。**

附件定位：`tools/source_intake_readonly_shared.py:358–397`。

### B. `authority bucket` 不是公司或客户权限

目前可见的过滤主要区分知识状态和支持角色。它有治理价值，但不能证明：

> 代理人甲不能读取代理人乙的客户；团队甲不能读取团队乙获授权的内部资料；撤销权限后缓存与引用也不可访问。

不要把沙箱里的 `allowed_roles` 名称理解成已经接入真实用户目录和服务端访问控制。

附件定位：`tools/source_intake_readonly_shared.py:225–245,278–296`；R1.5 `:3395–3408`。

### C. 150ms 不是产品响应速度

代码原文写的是：

> `local adapter p95 <= 150ms; not production end-to-end SLO`

这个实验不调用真实网络、数据库、模型和线上检索。它既不是本次测量，也不能推出“保险助手 150ms 内回答”。

R1.6 的历史通过结果同样限定在一次性影子资料库和受监督实验，不证明正式 Obsidian 写入、真实 IAM、模型质量或生产运行。

附件定位：R1.5 `:1–10,2872–2890`；历史 `summary.json:235–254`。

## 1.3 哪些设计确实应该保留？

不应因为系统尚未产品化，就把已经做对的部分推倒。

建议保留：

**来源原文与摘要分离；关键判断有原文锚点；时间和适用范围独立表达；相似不等于支持；用户反馈不能自动成为事实；能回答不等于能采取行动。**

尤其要指出：你们**已经设计了** `valid_from`、`valid_until`、`supersedes`、`applies_to` 等概念，并明确“旧”不自动等于“无效”。问题不是缺少这些想法，而是尚未证明它们在保险服务请求中被正确执行。

附件定位：`SCHEMA.md:1253–1312`；`FUSION_ARCHITECTURE_V0_2_DRAFT.md:824–945,3196–3412`。

# 二、首个 MVP：只做“会谈后跟进核对单＋有出处的回复草稿”

## 2.1 为什么选这个，而不是先做通用保险问答？

**通用问答范围太宽，难以界定什么算答好了，也很容易退化成“把 PDF 接到模型上”。**

“会谈后跟进”则有明确触发点、输入、交付物、人工责任和完成时间，比较容易检验产品是否真正节省工作。

但这仍然是一个**待验证的优先选择**，不是已经证明存在的需求。第一阶段必须拿它与团队现在的做法比较，包括公司现有工具和人工模板。

### 建议的首版边界

| 项目 | MVP 定义 |
|---|---|
| 用户 | 本人＋同一业务范围内 3–5 名成员；指定一名有相应业务能力的审阅人和资料负责人 |
| 资料范围 | 一个公司、一类产品、约 10–30 份明确获准处理的资料；数量是控制试点范围的建议，不是成功标准 |
| 触发 | 一次客户沟通结束后，需要整理待确认事项和下一步回复 |
| 输入 | 经最小化处理的会谈摘要、代理人选定的产品、适用版本或保单批次；最初用合成案例验证 |
| 输出 | 已知事实、待补问事项、可核对的产品事实、内部回复草稿 |
| 明确排除 | 自动选“最佳产品”、核保判断、理赔保证、自动发送、跨公司全市场比较、完整客户画像 |

**代理人选择待核对的产品，不让模型在首版里自由决定应该卖什么。**

## 2.2 交付物应该长什么样？

不是再生成一大段“看起来专业”的文字，而是一个方便核对的工作单：

| 区块 | 内容要求 |
|---|---|
| 客户已明确表达 | 只记录输入中实际说过的事实；推断另列，不能混写 |
| 仍需补问 | 标明缺少什么，以及缺少它会影响哪项判断 |
| 产品事实核对 | 每个关键事实附文件名、版本、页码或段落、适用范围 |
| 回复草稿 | 使用已支持的事实，保留必要限定，不写无依据的保证 |
| 人工确认 | 标出必须确认的数字、保障条件、除外事项、版本和措辞 |

例如，客户问：

> “这个是不是任何情况下都能赔？”

合格输出不应是把“保障全面”写得更委婉。它应该先指出：这属于绝对化表述，需要核对合同责任、除外责任及具体事实；没有取得适用条款时，不生成赔付承诺。

**“知道什么时候不能回答”是这个流程的一部分，不是失败后才加上的免责声明。**

## 2.3 三个人工确认点不能省

**输入确认：**代理人确认摘要没有把猜测写成事实，并确认产品和保单范围。

**事实确认：**审阅关键条款、数字、条件和引用；涉及适合性或其他专业判断时，不能仅凭系统生成结果放行。

**对外确认：**符合相关业务资格及公司要求的人，决定最终是否使用、怎样使用。系统不自动发送。

纠错必须形成闭环：

> 使用结果 → 标记错误类型 → 负责人处理 → 新资料或新 Skill 版本 → 重跑相关案例 → 再发布。

“这句说得不顺”和“适用了错误保单版本”必须分开统计，不能都进入一个笼统的“差评”池。

## 2.4 功能顺序

| 功能 | 建议顺序 | 原因 |
|---|---|---|
| 有范围的知识核对 | 首版内部能力 | 为该工作单提供证据，不扩成无限问答入口 |
| 会谈摘要整理＋补问＋回复草稿 | **首个完整闭环** | 可量化完成时间和修改负担 |
| 有限产品比较 | 下一阶段 | 先解决同口径、版本、币种、保障条件和缺失项问题 |
| 录音转录 | 后续单独设门槛 | 增加录音授权、第三方处理、语言识别及关键事实误听风险 |
| PPT | 更后 | 应渲染已经确认的事实，不让演示生成器重新“创作”保险结论 |
| 自动跟进、跨工具 Agent | 最后再评估 | 先证明内容质量，再讨论执行权限 |

## 2.5 首轮甚至不必自建完整产品

建议先做一个“人工组织资料＋固定模板＋公司允许的模型或工具”的对照流程。

若这已经满足团队需求，自研系统必须额外证明至少一项：

**版本治理更可靠、引用核对更省时、权限更符合需求、重复操作显著减少，或维护效率更好。**

否则，最合理的成果可能是一个团队维护的资料包与 Skills，而不是一个新 App。

BYOK——让每个人自带 API Key——也不是首版的必要条件。它会增加密钥管理、供应商差异、计费解释和支持负担，且不会自动消除你们对资料处理的责任。

# 三、最小架构：保留边界，减少平台化

## 3.1 建议的最小链路

```text
Obsidian 内部工作台
    ↓ 资料使用权检查＋内容审阅
版本化发布资料集
    ↓ 解析、分块、构建可重建索引
一个受控后台
    ├─ 登录与服务端权限
    ├─ 产品／保单批次／版本过滤
    ├─ 检索原文与必要上下文
    ├─ 一个固定业务 Skill
    └─ 调用一个获批准的生成模型
    ↓
结构、引用、数字与适用范围检查
    ↓
代理人核对界面
    ↓
人工决定是否对外使用
    ↓
错误归因与新版本发布
```

**这不要求微服务、图数据库、多 Agent、MCP 写入、自动装插件或专门的桌面应用。**

一个后台、一个合适的数据库和受控文件存储，可以作为小试点的逻辑基础；是否满足公司的实际安全要求，仍需具体部署审查。这里是组件边界建议，不是某个廉价主机方案已足够的承诺。

## 3.2 三种“权威来源”应明确分开

| 区域 | 谁说了算 | 不应混淆成什么 |
|---|---|---|
| 内部编写区 | Obsidian/VAKS 工作文件和审阅流程 | 不等于所有内容都可供在线回答 |
| 在线知识区 | 经批准的发布清单及对应内容版本 | 不能由未发布工作文件静默覆盖 |
| 客户业务记录 | 独立受控的数据记录与权限、保留政策 | 不能仅当成可随意重建的检索缓存 |

这意味着蓝图里“Markdown 是权威、SQLite 是派生缓存”的个人知识库原则，**不能不加区分地套用到客户业务数据库**。

同样，“服务异常就退回直接读 Markdown”在个人资料库里可能方便；在多人产品中，如果这绕过权限和发布门槛，就不能作为降级方案。

附件定位：`IMPLEMENTATION_BLUEPRINT.md:426–454,664–670`。

## 3.3 发布和撤回是试点前必补，不是规模化后再做

最小发布对象至少应表达：

> 资料 ID、原始来源、版本、适用范围、使用权范围、审阅责任人、发布时间、内容校验值、关联索引版本、撤回状态。

流程不必复杂，但要保证：

**发布资料与索引对应；工作区改动不会自动上线；撤回不必等下次批量重建；缓存、引用入口和排队任务同样受撤回控制。**

已经发出去的回复或导出文件无法靠“删除索引”收回，因此还需要标记受影响任务，让负责人决定是否更正。

AWS 官方知识库说明也明确区分源文件变化与同步后的重新解析、分块、嵌入和索引更新；它证明“更新是需要管理的过程”，并不证明本项目已经具备即时撤回。:chatgpt-content-reference{index="0"}

## 3.4 权限必须在模型之外执行

建议后台至少在以下位置执行授权：

**检索前、读取原文时、拼接客户上下文时、返回引用时，以及输出释放前。**

用户不能通过修改请求里的 `customer_id`、提示词或 Skill 文本改变权限。缓存也应绑定团队、用户权限范围和发布版本，不能仅以问题文本作为缓存键。

微软的公开 Copilot 架构强调，访问组织资料仍受当前登录用户的既有权限约束。可借鉴的是这个责任位置，而不是“用了类似分层，所以 VAKS 也获得相同安全性”。:chatgpt-content-reference{index="1"}

## 3.5 首版可以不建完整客户库

“客户资料应独立管理”是正确边界，**但第一天不一定需要长期客户画像、CRM 同步或跨会话记忆**。

首版可以只使用任务级的必要上下文，不自动沉淀为共享知识。不过，即使不长期保存，传输给模型、临时文件、日志、错误追踪和缓存仍然构成需要控制的数据路径。

Google 的公开 RAG 参考架构将资料摄入与在线服务分开，后者再组合检索内容并调用模型。这是常见架构安排，不是 VAKS 的独特性，也不证明香港保险数据可以任意经过相同服务。:chatgpt-content-reference{index="2"}

## 3.6 检索首先要解决“适不适用”，再解决“像不像”

建议硬过滤优先于相似度排序：

> 用户可访问 → 公司和产品范围正确 → 保单批次及版本适用 → 未被禁止使用 → 再做相关性排序。

需要区分**新销售资料**与**旧保单适用条款**。新版本发布，不能自动使旧合同资料失去适用性；旧版本也不能因为相似度高，就拿来解释新产品。

还要保留“条款＋定义＋除外责任＋脚注”的关联，不能只召回最正面的保障描述。

这些规则优先于是否采用向量数据库或 Jev。全文索引、向量或混合检索的选择，应由具体漏检案例决定，而不是把“更高级的检索组件”当成效果保证。

# 四、资料使用权、客户数据与维护：这是可行性核心，不是最后补一页合规说明

## 4.1 先把四种权限拆开

以下是建议的上线前判断框架，**不是对任何保险公司授权或法律例外的确认**。

| 权限层次 | 需要明确的问题 |
|---|---|
| 可以阅读 | 资料公开，或代理人能在公司系统看到，是否只说明有阅读权限？ |
| 可以保存及处理 | 是否允许复制、OCR、分块、建立索引、上传云服务？ |
| 可以提供给别人 | 是否允许团队共享、向客户引用、提供原文件或跨公司使用？ |
| 可以交给第三方 AI | 哪些供应商、地区、保留方式和用途得到允许？是否涉及再训练或再使用？ |

**客户的同意不能代替保险公司对内部资料的授权；代理人有账号，也不能自动证明可以把资料搬到自建服务器或第三方模型。**

对于公开文件，不能把“公开可读”直接解释成“可全文复制、再分发和商业再利用”。反过来，也不应一概断言所有处理都必须另取许可——具体许可条款和法律例外需要针对用途确认。

本次没有取得足够的现行官方版权/AI 例外材料，不能将任何尚待核实的文本与数据分析例外当作项目的授权基础。**试点应先选权利清楚的资料，而不是押注一个尚未确认适用的例外。**

## 4.2 香港个人资料要求：新增模型就是新增处理路径

私隐专员公署的 Agentic AI 指引涵盖目的与最少收集、准确性及保留期限、用途限制、安全、第三方处理，以及人工监督等问题；它还特别讨论长期记忆、工具和插件带来的风险。它是治理指引，不是对某个产品的合规认证。:chatgpt-content-reference{index="3"}

对本项目，我建议将这些要求落成一张实际的数据流清单：

| 数据 | 可能经过的服务 | 首版建议 |
|---|---|---|
| 产品原文片段 | 自建服务器、生成模型；未来可能还有 Jev | 仅使用获准资料，明确第三方处理范围 |
| 客户会谈摘要 | 输入端、后台、模型、任务记录 | 最小化，不默认发送完整聊天历史 |
| 原始录音 | 上传、对象存储、ASR、日志与备份 | 首版排除 |
| 客户身份和敏感细节 | 可能意外出现在提示、日志、反馈中 | 默认不需要；明确拦截与处理规则 |
| 模型回复 | 任务界面、保存记录、导出和人工复制 | 标明内部草稿；权限和保留政策同样适用 |

“去掉姓名”不应被当成已经充分匿名化的证明。业务场景、日期、疾病和家庭信息组合仍可能具有识别性。

对于第三方服务，应逐项确认处理地区、分包商、保留时间、删除、事故处理和用途限制。**“不用于训练”与“不保留”“不跨境”“公司已批准”是不同命题。**

我没有取得足够的研究时点官方依据来确认《私隐条例》第 33 条的最新生效状态，因此**不以“该条尚未生效”作为可以任意出境处理的依据**。

## 4.3 录音不是“加一个转录 API”那么简单

后续加入录音前，应先明确：录音目的、通知方式、谁可以接触、转录供应商、保留与删除规则，以及公司是否允许这种处理。

还应检验粤语、普通话、英语混说时，对金额、日期、否定词、产品名和客户自述的识别错误。一般字错率低，不代表关键保险事实可靠。

我没有把“任何录音都必须所有人同意”写成香港法律的一概结论；这里提出的是产品试点的风险控制条件，而不是替具体场景作法律裁断。

## 4.4 保险业务责任不能交给“内部助手”这个名称

本次定位到了 IA 操守要求，但正式守则全文的直接访问未成功。港大 CLIC 对其原则的说明包括客户最佳利益、谨慎与胜任、准确披露、适合性和利益冲突等；这是辅助法律解说，**不能代替现行守则全文及公司的具体要求**。:chatgpt-content-reference{index="4"}

因此，本次评审不能批准真实客户销售使用。试点设计应避免把“只是草稿”“只是内部工具”当作责任豁免。

对外产品建议、适合性判断和关键销售表述，必须有符合该业务要求的人员及公司流程承担责任，而不是由 VAKS 的 `reviewed` 标签、Codex 审阅或模型置信度代替。

## 4.5 维护不是一次导入，而是一项持续业务

每份重要资料至少应有**负责人和备份负责人**。更新过程建议保持简单但完整：

> 发现新版本或通知 → 判断影响哪些产品与保单 → 核对差异及引用 → 更新相关 Skill 和案例 → 发布 → 停用不再适用的输出路径。

应区分：

- 正常内容更新；
- 仅对新销售生效的调整；
- 对特定旧保单仍适用的历史版本；
- 紧急停止提供的内容；
- 到期需要复核，但尚不能断定失效的资料。

核心经济问题不是“能不能抓取很多资料”，而是：

**每维护一组资料，能稳定支持多少真正有用的工作？维护一小时，是否减少了更多核对和返工？**

如果没有持续资料负责人，产品会逐渐变成**引用看起来完整、实际适用性越来越不可靠**的系统。

# 五、Agent 与 Jev：首版都不是必要依赖

## 5.1 完整 Agent 不必要

首个流程的步骤已经可明确列出，不需要模型自行规划到哪里找资料、装什么工具或执行什么操作。

建议首版采用：

**固定工作流＋一个生成模型＋确定性后台检查＋人工确认。**

资料和客户输入均按不可信内容处理，不允许其中的文字变成系统指令；不开放 shell、浏览器登录、任意网络访问、自动发信或自由安装 Skills。

这里的重点不是声称完全消除提示注入，而是减少模型出错后可影响的范围。

## 5.2 Jev 的身份与能力已经核实

本次官方文档将 Jev 定位为 TypeSafe AI 的 **System One 决策模型**。读取时当前版本为 **`jev-1.13.0`**，通过云 API 对文本状态作类型化判断；它不是用来生成长篇回复的模型，也不是向量检索本身。不能仅凭“System One”名称进一步断言其底层完全不用语言模型或某种具体网络结构。:chatgpt-content-reference{index="5"}

官方模型页列明：文本输入，每百万输入 token **US$0.042**，输出免费；总请求和状态均有上下文限制。英语是主要训练语言，其他语言表现并不等同；别名可能自动指向新版本。:chatgpt-content-reference{index="6"}

因此，香港中英条款和粤语表达需要专门验证，不能继承英文演示的效果结论。

## 5.3 官方局限直接影响你们的候选用途

Jev 1.13 的限制文档明确提示：

**数值计算及计数不可靠；日期先后和区间比较不可靠；复杂否定及间接判断较弱；无关长上下文会影响结果；恶意输入可以干扰判断。**

官方也建议把算术和日期比较留在代码中。类型化输出并不等于事实正确，更不等于保险专业判断或访问授权。:chatgpt-content-reference{index="7"}

### 三个接入位置的判断

| 接入位置 | 判断 | 首选替代 |
|---|---|---|
| 任务路由 | **首版不需要** | 只有一个主要流程，让用户明确选择即可 |
| 片段筛掉 | **最需谨慎** | 错筛可能删除除外责任和反证；先靠适用范围与结构规则 |
| 候选重排 | **后续最值得试验的位置** | 在可靠召回之后，与不重排、规则或其他重排器比较 |
| 金额、日期、权限、保险适合性判定 | **不应交给 Jev 决定** | 数据校验、确定性规则、真实授权系统及专业人工 |

官方重排 cookbook 是厂商在有限法律语料和查询上的示例，并非香港保险端到端验证，也不是你们当前检索链路的性能证明。:chatgpt-content-reference{index="8"}

## 5.4 云 API 与资料处理风险

本次确认了公开云 API；**没有核实可供你们直接采用的公开模型权重或通用自托管方案**。SDK 可用或开源，不等于模型可以本地部署。

TypeSafe 表示不以客户请求训练模型，并提供面向企业的零数据保留安排；这不能解读成所有默认账户都不保存数据。具体保留、地区和合同适用仍须采购核对。:chatgpt-content-reference{index="9"}

只要把公司条款或客户上下文交给 Jev，就新增了一个需要批准和管理的处理方。

## 5.5 真正有意义的后续比较方法

先固定同一批候选证据，再比较：

**不加重排、确定性规则、生成模型重排、Jev，以及有授权条件下的其他重排器。**

建议使用独立保留的中文、英文及混合表达案例，包含旧保单、否定、冲突、缺资料和除外责任。评价应至少看：

**关键证据是否保留、反证是否被删、最终引用是否支持结论、人工修改时间、总调用成本、端到端延迟。**

不能只看重排分数，或只看 Jev 这一次 API 有多快。本轮没有执行这些测试。

# 六、竞争差异：目前只有一部分成立

## 6.1 先确认产品身份

| 名称 | 本次确认的对象 | 仍需保留的不确定性 |
|---|---|---|
| WorkBuddy | 腾讯的 WorkBuddy 产品体系，包括桌面、团队和企业能力 | 不同版本、采购地区与套餐不能混为一谈；未核验具体安装构建号 |
| Grok Bot | `docs.x.ai/grok-bot` 官方文档中的持续运行 Bot 产品；页面现标示 SpaceXAI | 不能等同普通 Grok 聊天或社交平台机器人；具体计划、地区和开放状态须再核 |
| MUSE | 可核实的强候选是 **Meta 于 2026-09-08 介绍的 Muse 个人 Agent** | 原讨论没有链接，无法确认一定指这个产品；以下比较仅针对该候选 |

这些身份依据分别来自腾讯产品文档、x.ai 官方 Bot 文档和 Meta 官方 Muse 说明，不沿用旧对话中的称呼推断。:chatgpt-content-reference{index="10"}

## 6.2 “我们有知识库和 Skills，他们只是通用聊天”不成立

腾讯 WorkBuddy 官方团队页面已经列出共享知识库/RAG、团队 Skills、Agent 版本管理、角色权限、访问日志和预算管理等能力。它还公布了 Team 计划价格。**所以“团队知识库＋Skills＋管理后台”不能作为你们的独有差异。**这些是厂商公开能力，未在本次独立实测。:chatgpt-content-reference{index="11"}

Grok Bot 官方说明包含可复用 Skills、定时或事件流程及跨工具操作。其安全文档同时明确：同一用户的 Bots 共享云电脑，不能把不同 Bot 当成安全边界；删除 Bot 也不等于清除云电脑文件和会话。:chatgpt-content-reference{index="12"}

Meta Muse 的官方说明包含专属云电脑、自定义 Skills、连接器和子 Agent，也明确承认 Agent 仍会犯错，因此在运行环境设置外部约束。这是其公开设计，不是保险专业能力验证。:chatgpt-content-reference{index="13"}

## 6.3 真正可能成立的差异

你们可能有价值的不是“也有这些组件”，而是：

| 潜在差异 | 怎样才算成立 |
|---|---|
| 香港保险版本适用管理 | 实际减少错版本、错保单批次和漏条件，不只是有字段 |
| 资料持续更新 | 新通知能被负责人及时处理，并更新受影响输出 |
| 保险跟进流程质量 | 比通用工具减少补问遗漏、返工和人工核对时间 |
| 引用体验 | 代理人能快速核对原文，而不是获得一串不方便打开的链接 |
| 团队专属资料与方法 | 有合法使用范围，能够稳定维护，且真正带来效果 |
| 团队使用习惯 | 成员在没有推动或新鲜感时仍持续使用 |

**这些都是可以验证的假设，不是现有护城河。**

公开产品文件本身不是排他资产，Skills 文字也容易被模仿。更有机会形成持续价值的是：

> 获授权资料＋版本与适用性整理＋经过真实任务检验的工作流＋持续维护服务。

但如果维护人离开就停止更新，或所有核对仍靠你本人兜底，形成的可能只是个人服务能力，而不是可扩展产品能力。

## 6.4 保险公司内部工具必须纳入基线

本次没有取得你们所属公司的工具清单，不能声称其没有相似能力。

正式评估应把公司现有的资料门户、建议书工具、客户管理、需求分析和获准使用的 AI 工具列入对照。**已有工具的边际成本和授权便利，可能比另建系统更有优势。**

你们不必替代整套公司系统，只需证明一个现有流程确实做得不够好，而你们能以更低总负担改善它。

## 6.5 “保有據”名称

本次做过“保有據／保有据”的普通网页检索，但没有得到足以确认同名或排除冲突的可靠结果；也定位了知识产权署查询入口，**没有完成商标注册库、相似文字、读音及相关类别的正式检索**。

因此，名称只能继续作工作暂名，不能据此宣称可注册或商业使用无冲突。“有据”也不应在产品文案里扩张成“保证正确”或“已经获得公司认可”。

# 七、成本与延迟：API 很可能不是主要矛盾

## 7.1 估算口径

以下均为**公开价格＋明确用量假设的情景计算，不是实际账单、测得使用量或供应商采购建议**。

研究时点 Google Cloud 标准价格表列示：

| 服务 | 本次采用的公开价格 |
|---|---:|
| Gemini 2.5 Flash | 输入 US$0.30／百万 token；输出 US$2.50／百万 token |
| Gemini 2.5 Pro | 在本例短上下文范围内，输入 US$1.25；输出 US$10／百万 token |
| Jev 1.13 | 输入 US$0.042／百万 token；输出免费 |
| Google Speech-to-Text V2 标准 | 低用量档 US$0.016／音频分钟 |

Google 生成输出价格包含计费的响应和推理输出；ASR 多声道可按各声道累计计费。价格、型号可用性、地区和企业条款仍需采购时确认。:chatgpt-content-reference{index="14"}

本例不采用免费额度、缓存折扣或承诺用量折扣，也不将较高价格解释为已经证明更适合保险。

### 每次任务假设

- 输入 **8,000 token**：包含指令、必要摘要及检索资料。
- 总计费输出 **1,500 token**：不是只计算用户看到的文字。
- 预留 **10% 额外计费用量**，用于敏感性估算，不代表实际失败率。
- 汇率按 **US$1＝HK$7.8** 计算，仅是换算假设。

公式：

\[
单次生成成本
=\frac{输入量×输入单价+输出量×输出单价}{1,000,000}×1.1
\]

## 7.2 文字任务成本

| 情景 | 月任务量假设 | Flash 单遍／月 | Pro 单遍／月 | 两遍同等预算生成／月 |
|---|---:|---:|---:|---:|
| 本人使用 | 1 人×5 次×20 天＝100 | US$0.68 | US$2.75 | US$1.35–5.50 |
| 小团队 | 5 人×5 次×20 天＝500 | US$3.38 | US$13.75 | US$6.77–27.50 |
| 较大使用量情景 | 20 人×10 次×20 天＝4,000 | US$27.06 | US$110.00 | US$54.12–220.00 |

这只包含表中定义的文字生成调用，不含资料解析、额外检索服务、存储、服务器、日志、监控、专业审阅、维护和开发。

**再加一遍模型核对，只是另一次判断，不自动获得独立事实验证能力。**

## 7.3 加入 Jev 会怎样？

假设每次比较 20 个候选，每项合计 700 输入 token：

\[
20×700×0.042÷1,000,000
=US\$0.000588/次
\]

500 次／月约 **US$0.294**。

单看 API 很便宜。但对 Flash 而言，省去 2,000 输入 token 也只节约 **US$0.0006**，与这个 Jev 情景费用接近，尚未计入接入、监控、评测和资料处理审批。

因此：

**Jev 值不值得加入，主要由质量改善和实际端到端表现决定，不应由“看起来便宜很多”的单价倍数决定。**

## 7.4 音频会增加一层独立成本

假设每月 100 次、每次 30 分钟、单声道：

- 总音频量：3,000 分钟。
- V2 标准转录：约 **US$48／月**。
- 官方另列低优先级动态批次 US$0.003／分钟，相同音频量约 US$9；但它不是同等延迟服务。:chatgpt-content-reference{index="15"}

仍未计转录校对、存储、传输及后续摘要。不能只因转录 API 便宜，就认为录音业务闭环成本低。

## 7.5 维护与人工可能比模型费用大得多

以 500 次任务／月为例，作一组**非市场报价、非实测**的预算假设：

| 项目 | 假设 |
|---|---:|
| 资料维护 | 6–12 小时／月 |
| 用户支持与问题处理 | 2–4 小时／月 |
| 时间价值 | HK$250／小时 |
| 基础设施预算占位 | US$20–100／月；不保证满足企业安全要求 |
| 生成模型 | 上表单遍预算 |

按这组假设，维护、支持、基础设施和生成用量合计约 **HK$2,182–4,887／月**。

如果每次人工核验还需 3–8 分钟，500 次对应 **25–66.7 小时**。不过，这部分不能一概视作新增成本：原流程可能本来就需要核对，正确方法是比较**原流程与新流程的总完成时间**。

不计初期开发和整理费用，上述后台开销意味着：

> **500 次任务／月时，每次净节约约 1.05–2.35 分钟，才抵消这组假设的月度开销。**

这里的“净节约”已经扣除新流程里的输入整理、核验和修改时间，不能再重复扣一次人工核验费用。

还有一个重要对照：WorkBuddy 官方页面列 Team 计划为 **US$40／人／月，含规定 Credits**，5 人即 US$200／月。它是否够用、是否符合公司要求尚未验证，但足以说明：**只拿自研 API 费与现成产品订阅费相比，会严重低估自研成本。**:chatgpt-content-reference{index="16"}

初次资料整理、开发、审批、专业审查、事故处理及合规部署费用，尚未包含在上述收支比较中。

## 7.6 延迟只能给敏感性模型，不能冒充实测

完整机器延迟应计算：

\[
T=认证+检索+重排+模型等待+生成+核对+排队/重试
\]

举一个**纯假设演算**：

- 非模型步骤：0.2–1.5 秒；
- 模型初始等待：1–5 秒；
- 1,500 输出 token 的有效生成吞吐：20–80 token／秒。

结果约 **20–82 秒**；额外排队、限流、推理等待和重试可能继续增加时间。

这**不是测得区间、不是 p95、更不是服务承诺**。实际结果必须按选择的模型、输出长度、网络和并发测量。

Jev 也不应被视为零延迟。例如，假设 20 项候选、并发 5、每波 0.2–0.8 秒，仅重排就增加约 0.8–3.2 秒；这些同样只是敏感性参数。

最重要的指标最终应是：

**从会谈摘要准备好，到代理人得到可用且核对完成的回复，总共花了多久。**

# 八、实施顺序与验收：先证明值得做，再证明能稳定做

以下数量与阈值是**建议的试点门槛，不是行业标准，也不是已经达成的结果**。

## 阶段 0：准入与基线，不先扩架构

确定一个产品范围、一名资料负责人、一名业务审阅责任人；明确哪些资料可以保存、处理和交给哪些服务。

同时记录现有流程：每周真实任务量、平均完成时间、常见错误、现有公司工具能做什么。

**验收：**资料范围、处理方和责任人能说清楚。无法确认授权的材料不进入模型；仍可用合成案例验证流程结构。

**调整条件：**如果主要痛点只是找不到一个官方链接，先改资料目录，不开发复杂助手。

## 阶段 1：人工辅助的流程验证

使用约 **30–50 个有代表性的合成或获准处理案例**，让现有流程与拟议工作单完成相同任务，记录核验后的总时间与错误。

这一步可以使用现成工具，不要求已经开发服务器。

**验收：**

- 输出格式确实帮助代理人完成工作，而不是增加阅读负担；
- 关键事实可以回到适用原文；
- 识别出实际反复出现的节省时间点；
- 与原流程相比，质量没有明显退步。

**停止或缩小条件：**工作单需要大量重写，或“整理输入＋检查输出”比原来更慢。

## 阶段 2：补齐最小技术闭环

只实现必要的发布资料集、后台身份权限、范围过滤、引用核对界面及错误记录。

建议准备 **60–100 个有针对性的挑战案例**，包含：

> 错用户、错客户、撤销权限、旧版本、缺失资料、除外责任、冲突条款、提示注入、缓存命中和更新切换。

**验收重点：**

| 维度 | 建议门槛 |
|---|---|
| 越权 | 预设跨用户、跨客户和撤权案例全部拒绝；不得以提示词作为权限 |
| 来源 | 所有关键产品事实均能定位到适用原文 |
| 版本 | 不能将新销售版本自动套到旧保单 |
| 关键错误 | 上线前测试中不能留下未解决的关键错误路径 |
| 失败行为 | 缺资料、冲突或范围未知时，明确补问或限制回答 |
| 撤回 | 原文、索引、缓存和引用入口一并受到控制 |
| 变更 | 发布或 Skill 更新后能重跑受影响案例 |

这里的关键错误包括：保障或除外含义反转、错误保单版本、关键数字无依据、把推断写成客户事实，以及越权泄漏。

**100 个案例没有发现错误，不等于现实中可以承诺零错误。**它只是进入更小范围真实试点的必要证据之一。

## 阶段 3：3–5 人、约四周限量试点

建议累积约 **100 次以上符合范围的任务**，并分别记录原始草稿错误和最终人工输出错误。不能因为人工纠正了，就把系统最初的严重问题从统计里删掉。

重点观察：

**配对任务时间、引用核对负担、维护时间、每个可接受结果的总成本，以及团队是否主动重复使用。**

可以先设一个创始团队式门槛：5 人中至少 3 人在四周里有三周主动使用；这个数字仅用来排除“只体验一次”的假象，不是市场验证标准。

经济门槛则应随实际数据重算。以上述成本情景为参考，若只节省几十秒，却新增固定维护工作，就不支持继续扩大开发。

## 阶段 4：只扩展已经证明值得扩展的部分

有限比较、录音和 PPT 分别设验证门槛，不打包一起上线。

跨公司服务应重新审查授权、资料隔离、合同、运营和支持能力，不能直接继承本团队试点的通过结论。

# 九、保留、修改、补齐与暂缓：优先级清单

| 处理方式 | 最高优先级内容 |
|---|---|
| **保留** | 原文与摘要分离、来源锚点、时间和适用性、反证及缺失项、反馈不自动成真、回答与行动分离 |
| **简化** | 首版必填元数据、普通查询流程、通用证据对象数量；只保留当前业务实际消费的字段 |
| **修改** | 把知识状态过滤与真实 IAM 分开；将 Markdown 权威限制在编写区；将保险审阅责任与工具/模型审阅分开 |
| **补齐** | 资料使用权登记、发布与撤回、长文与表格处理、真实权限、引用核对 UI、业务测试集、成本与人工时间记录 |
| **暂缓** | 图数据库、多 Agent、自动技能安装、MCP 写入、跨客户长期记忆、完整 CRM、ASR、PPT、应用商店 |
| **有证据再加** | 向量/混合检索、Jev 重排、第二遍生成；用明确失败案例或经济收益触发，而不是因技术流行而引入 |

对当前代码复用，应理解为**保留实现思想与可审查模块，再做适配和验证**，不是把片段直接搬到服务器就获得生产保证。

# 十、继续、调整、停止投入的条件

## 继续

当一个明确范围内的业务流程同时满足：

**资料权利清楚；有人持续维护；关键输出能核对；权限测试过关；成员重复使用；净节省时间足以覆盖新增负担。**

这时值得投入最小工程化。

## 调整

当业务价值存在，但自研系统不是最优载体时，应接受以下结果：

**用现成工具承载；只保留授权资料包与 Skills；减少产品范围；采用公司允许的处理环境；去掉 Jev 或其他不能证明收益的组件。**

这不算项目失败。你们要验证的是工作价值，不是证明必须拥有某种架构。

## 暂停或停止扩大投入

出现以下情况时，应停止相应真实业务使用或扩大投入：

**无法取得必要资料/处理授权；出现系统性越权或资料泄漏；重复发生无法有效阻断的关键条款错误；无人维护版本；两个有边界的改进周期后仍比现有流程更慢或更贵。**

安全问题应先停受影响路径，调查范围；不是靠加一段免责声明继续运行。

## 最终建议

**推进“保有據的一个业务流程”，不要先推进“完整 VAKS 平台”。**

把首轮目标固定为：

> **在一个获授权的产品范围内，让代理人更快完成会谈后核对和回复准备，同时能够发现缺资料、错版本和不该作出的承诺。**

如果这件事成立，VAKS 的来源、版本、适用性和反馈机制有实际复用价值；如果这件事不成立，再多 Agent、Jev、图谱、录音和 PPT，也不会自动创造持续价值。
