# Intake Metadata Prefill Optimization

## Plain Rule

```text
Yes, prefill a few discovery fields at intake.
No, do not prefill authority.
```

This optimization is about making future retrieval smoother.

It is not about proving the source is true, reviewed, adopted, or action-ready.

## What To Prefill

Good source-card prefill fields:

```yaml
topics: []
entities: []
aliases: []
content_form:
language:
version_or_time_scope:
tags: []
```

Keep it small:

```text
topics: 1-2 from the candidate topic registry
entities: 0-5 clear names from title/source/metadata/body
aliases: only obvious synonyms or product/library names
tags: weak recall only, optional
```

## Two Write Paths

### Path A: Confirmed During Explicit Intake

Use this when the user explicitly asked to intake/create a source card, and the
metadata is obvious.

Allowed:

```text
content_form from source type
language from text or transcript metadata
topics from controlled candidate topic list
entities from visible title/source/body metadata
version_or_time_scope from captured date, release date, commit, paper date, or
explicit version
```

Record it directly on the source card as confirmed discovery metadata.

### Path B: Suggested Sidecar

Use this when the metadata is uncertain, generated by model guesswork, or not
confirmed by the user/task.

Write:

```yaml
record_kind: intake_metadata_suggestion
persistent_main_note_allowed: false
default_retrieval_allowed: false
suggested_topics: []
suggested_entities: []
suggested_content_form:
suggested_language:
suggested_version_or_time_scope:
suggested_routing_hint: []
```

The sidecar can help review.

It cannot enter default retrieval as if confirmed.

## Forbidden Prefill

Never prefill these into source-card tags, topics, or entities:

```text
reviewed
approved
adopted
use-this
best-practice
truth
safe
action-basis
decision
verified
high-confidence
for-vaks
do-not-borrow-for-vaks
adopt-for-vaks
```

Never prefill project borrowing judgment into a generic source card:

```text
good for VAKS
bad for VAKS
adopt in VAKS
avoid for VAKS
do not borrow for this project
```

Those belong in a project overlay or review layer.

## Why It Improves Retrieval

Without prefill:

```text
retrieval has to find the right source from title/body wording only.
```

With prefill:

```text
topic filters can find the source
entity filters can aggregate related sources
content_form can route article/repo/video/paper differently
language can choose query language and translation behavior
version_or_time_scope can prevent stale context from entering current packs
```

## Retrieval Order

Prefill metadata does not change the main retrieval order:

```text
1. authority/status/project/path-role hard filter
2. topic/entity/tag/content_form/language filters inside allowed lane
3. lexical/vector/rerank inside allowed lane
4. raw or reviewed anchor check for action-facing support
```

Metadata improves step 2.

It does not bypass step 1 or step 4.

## Human Experience Target

Before:

```text
I remember we saved something about DataChain and context packs, but search only
finds it if the exact words appear in the body.
```

After:

```text
Search by topic `context-pack` or entity `DataChain`, and the source card appears
as raw drilldown / candidate orientation depending on lane.
```

## Recommended MVP

Add a small lint before mainline writeback:

```text
topic count <= 2 on source cards
topics must be in candidate topic registry
authority/project-adoption words forbidden
suggestion sidecars must not be persistent/default retrieval
source metadata does not set action_basis_allowed
```

## Stop Point

Do not build:

```text
global ontology
mandatory tag taxonomy
automatic project adoption tags
truth confidence from tag match
heavy entity graph
```

This is a cheap retrieval helper, not a new knowledge layer.
